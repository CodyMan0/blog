> 초안. 데스크탑에서 대화하며 채운다.

## 배경 — 스토리북을 어디에 올릴 것인가

디자인 시스템 작업을 하면서 스토리북을 팀 전체가 볼 수 있는 곳에 배포하려고 했다. 처음엔 당연히 Chromatic을 떠올렸다. 스토리북 진영에서 사실상 표준처럼 이야기되는 도구였기 때문이다. 그런데 "정말 Chromatic이어야 하는가"라는 질문을 스스로 던지고 나니, 도구를 고르기 전에 우리가 스토리북을 왜 배포하려는지부터 정리해야 한다는 걸 알았다.

선택지는 세 가지로 좁혔다.

1. Chromatic
2. Amplify
3. EC2에 직접 구축

## Chromatic이 주는 것

Chromatic은 스토리북 전용 CI/CD 및 테스트 플랫폼이다. 조금 더 풀어 쓰면 UI 컴포넌트의 품질 관리 및 협업 도구다. 내가 정리한 강점은 세 가지였다.

첫째, 시각적 회귀 테스트(Visual Regression Test)다. PR을 올리면 CI 과정에서 모든 컴포넌트를 자동으로 스크린샷으로 찍고, 이전과 달라진 부분이 있으면 개발자에게 알려 준다. "이 PR이 의도치 않게 다른 컴포넌트의 모양을 바꿨는가"를 사람이 눈으로 뒤지지 않아도 된다.

둘째, PR별 프리뷰 링크다. PR이 올라오면 그 변경 사항이 반영된 스토리북 링크를 자동으로 생성해 댓글로 남겨 준다. 디자이너, 기획자, 동료 개발자가 그 링크에 들어가 실제 컴포넌트를 직접 조작해 보고, 코드를 몰라도 UI 리뷰에 참여할 수 있다. 리뷰가 끝나면 대시보드에서 승인을 눌러 피드백을 줄 수도 있다.

셋째, 배포와 버전 관리가 간단하다. 명령 한 줄로 끝난다.

## Amplify와 EC2를 견줘 보면

Amplify도 PR마다 프리뷰를 제공한다. 정적 호스팅과 PR별 프리뷰까지는 Chromatic과 크게 다르지 않다. 결정적인 차이는 시각적 회귀 테스트가 없다는 점이었다. 변경 사항을 사람이 일일이 확인하고, 기존과 다른 점을 직접 찾아내야 한다.

EC2에 직접 구축하는 방식은 정적 호스팅은 가능하지만 권장할 만한 선택이 아니었다. PR별 프리뷰도 직접 만들어야 하고, 시각적 회귀 테스트나 UI 리뷰 협업 도구도 없다. 설정 난이도만 매우 높았다.

세 방식을 표로 정리하면 이렇게 갈렸다.

| 기능 | Chromatic | Amplify | EC2(직접 구축) |
| --- | --- | --- | --- |
| 정적 호스팅 | O | O(권장) | O(비권장) |
| PR별 프리뷰 | O | O | 직접 구축 |
| 시각적 회귀 테스트(VRT) | O(핵심 기능) | X | X |
| UI 리뷰/협업 도구 | O | 프리뷰로 일부 가능 | X |
| 설정 난이도 | 매우 쉬움 | 쉬움 | 매우 어려움 |

## 결정을 가른 축 — 시각적 회귀 테스트

표를 놓고 보니 세 방식을 실제로 가르는 축은 하나로 좁혀졌다. 시각적 회귀 테스트를 자동으로 해 주느냐 아니냐였다. 나머지 항목은 Amplify로도 웬만큼 메워졌다.

그렇다면 질문은 이렇게 바뀐다. "우리 팀은 지금 스토리북을 무엇으로 쓰려 하는가."

- 목적이 단순히 스토리북을 볼 수 있게 띄워 두는 것이라면 Amplify가 충분히 훌륭한 선택이다.
- 스토리북을 UI 컴포넌트의 품질 보증 시스템으로 쓰고, 자동화된 테스트와 디자이너와의 효율적인 협업까지 원한다면 Chromatic이 맞는다.

```
스토리북을 왜 배포하나?
  ├─ "그냥 다 같이 보게 띄워두기"        → Amplify
  └─ "품질 보증 + 자동 시각 회귀 테스트"  → Chromatic
```

## 마무리 — 지금의 선택

나는 우선 Amplify로 가기로 했다. 지금 우리에게 필요한 건 스토리북을 팀이 함께 보는 것까지였고, 그 목적에는 Amplify로 충분했다. 시각적 회귀 테스트가 없어서 겪는 불편이 실제로 쌓이기 시작하면, 그때 Chromatic을 다시 꺼내 고민하기로 했다.

도구의 유명세로 결정하지 않고, 우리가 지금 필요한 기능이 무엇인지로 결정했다는 점이 이 판단에서 마음에 들었다. 표준처럼 불리는 도구를 고를 때도, 그 도구의 핵심 기능(여기서는 VRT)이 우리 문제와 맞닿아 있는지를 먼저 물어야 과한 도입을 피할 수 있었다.
