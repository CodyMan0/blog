## 들어가며

5월 말, 6월엔 이런 걸 하겠다고 예고했었다.

- **앱 마이그레이션** — Flutter에서 React Native로. 이전 웹 마이그레이션과는 조금 다른 방식으로.
- **백엔드 기초 학습** — 미오에서 데이터 설계로 제대로 데인 뒤라, DB 정규화·Node 동작 원리·모노레포를 기초부터 파보기로 했다.
- **의료기기 다나와 개편** — 5월 인터뷰에서 나온 피드백을 실제 제품에 반영하기.

그런데 6월은 계획 밖의 일이 더 많았다. Amplify에서 Vercel로 인프라를 통째로 옮겼고, 네이버 지도 API 장애를 수습했고, 이미지로 박혀 있던 텍스트를 마크업으로 걷어내는 SEO 작업을 했다. 그리고 크고 작은 미팅을 직접 이끌었다.

돌아보면 6월은 **팀장님이 열어준 변화의 물결에 올라탄 달**이었다. 5월에 합류하신 팀장님이 구조적인 문제들을 하나씩 건드리기 시작했고, 그 실행의 상당수가 6월에 내 손을 거쳤다.

---

## 1. Flutter → React Native 앱 마이그레이션

3~4월에 끝낸 웹 마이그레이션(Flutter-web → Next.js)의 **앱 버전**이 6월에 시작됐다. 팀장님이 오시며 "기존 앱을 웹 UI(웹뷰) 기반으로 개편하자"는 방향이 잡혔고, 프로젝트를 **모노레포**로 묶는 작업도 이때 함께 출발했다.

한 번 해본 마이그레이션이라 이번엔 조금 다르게 가보고 싶었다. 웹 때 배운 것 — _한 번에 갈아엎기보다 경계를 나눠 점진적으로, 그리고 AI에게 반복 작업을 최대한 위임하기_ — 을 앱에도 적용해보려 했다.

> ✍️ 채울 것 — 실제로 "다르게" 한 지점 한두 개(작업을 쪼갠 방식? AI에게 시킨 방식? 점진 vs 한 번에?), 6월 말 기준 어디까지 진행됐는지(범위·배포 여부), 앱이라 예상 못 한 차이.

---

## 2. 백엔드 기초 학습 — 미오가 남긴 숙제

5월 미오에서 *자주 바뀌는 도메인일수록 초기 데이터 설계가 중요하다*는 걸 몸으로 데었다. 그때 "다음 달엔 백엔드를 기초부터 제대로 보겠다"고 다짐했고, 6월이 그 달이었다.

마침 6월 초 실무에 **모노레포**가 등장했다. 미오에서 어렴풋이 겪은 구조(패키지 매니저·워크스페이스)가 실무로 들어오니, 공부와 실무가 맞물렸다. 계획했던 축은 세 가지였다 — **DB 정규화**, **Nest.js › Express › Node의 동작 원리**(프레임워크가 감춘 걸 벗겨보기), **패키지 매니저·모노레포**.

> ✍️ 채울 것 — 실제로 뭘 어떻게 공부했나(강의·책·실무 적용?), 가장 크게 남은 개념 하나, 못 한 게 있다면 왜 못 했는지(그것도 좋은 기록).

---

## 3. 의료기기 다나와 전면 개편 — 인터뷰가 제품이 되기까지

이 글의 백미다. 5월 의사 인터뷰에서 나온 이야기가 **6월 제품 변경으로 그대로 이어졌다.**

인터뷰에서 배운 핵심은 "**기기 정가 비교는 무의미하다**"였다. 의사가 실제로 보는 건 정가가 아니라 **실거래가·엔딩가·프로모션 추세**였고, 소비자 체감가를 가르는 건 **팁·소모품**이었다. 심지어 본사 직거래가 더 비싸고 영세 업체가 더 싼데, 고객은 정반대로 인식하는 경우까지 있었다.

그래서 개편은 "스펙 나열"에서 "**의사의 의사결정을 돕는 정보**"로 방향을 틀었다. 대분류 카테고리(초음파·영상·충격파)로 훑을 수 있게 하고, 프로모션·이벤트 정보를 얹고, 상세 이미지의 신뢰도를 높였다.

> ✍️ 채울 것 — 실제로 반영한 기능을 구체적으로(카테고리? 프로모션 알림? 찜?), 그리고 수치. 앰플리튜드 기준 상세 조회·데모 신청 유입이 있으니 함께 넣으면 최고다(예: 상세조회 3,459 · 데모 신청 21 — 실제 값 확인).

## 4. Amplify → Vercel 대이관

10월에 "아직은 Amplify"라고 미뤄뒀던 결정을, 6월에 실행했다. 인프라를 **Amplify에서 Vercel로 통째로** 옮겼다.

프리뷰 배포, 빌드 속도, 개발 경험(DX) — 옮길 이유는 계속 쌓여 있었다. 웹이 이미 Next.js로 넘어온 상황이라 Vercel과의 궁합도 좋았다.

> 이 작업은 회고에 다 담기엔 커서 따로 기술 글로 깊게 정리하려 한다 → _Amplify → Vercel 이관기 (작성 예정)_.

---

## 5. 네이버 지도 API 장애 후속 대응

6월엔 네이버 지도 API 관련 장애가 있었고, 그 수습과 재발 방지까지 맡았다. 외부 API에 의존하는 기능이 얼마나 취약할 수 있는지, 그리고 폴백과 모니터링이 왜 필요한지를 체감한 사건이었다.

> 증상·원인·대응은 트러블슈팅으로 따로 정리하는 게 맞을 것 같다 → _네이버 지도 API 장애 대응기 (작성 예정)_.

> ✍️ 채울 것 — 무슨 장애였나(지도가 안 뜸? 쿼터 초과? 스펙 변경?), 사용자 영향, 어떻게 막았나.

## 6. SEO 개선 — png를 html로

이미지로 박혀 있던 텍스트를 **시맨틱 마크업**으로 걷어냈다. 이미지 속 텍스트는 크롤러가 못 읽고, 접근성과 로딩에도 손해라 — 앞서 해온 SEO 작업들의 연장선이었다.

> 범위와 효과는 기술 글로 따로 → _이미지 텍스트를 마크업으로 (작성 예정)_.

---

## 7. 미팅을 주도하며

6월엔 개발자인 내가 크고 작은 미팅을 직접 이끌었다. 미오에서 *"코드보다 어려운 건 무엇을 만들지 합의하는 일"*이라는 걸 배운 뒤라, 이번엔 그 합의를 **내가 먼저 설계**해보려 했다.

> ✍️ 채울 것 — 어떤 미팅을 왜 내가 이끌게 됐나, 어떻게 준비하고 합의를 끌어냈나, 미오에서 배운 의사소통이 여기서 어떻게 이어졌나.

> 배운 것 — 개발자가 "무엇을 만들지"의 자리에 앉으면, 만드는 방식뿐 아니라 만들 것 자체를 바꿀 수 있다.
