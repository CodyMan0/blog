## 1. Amplify → Vercel — 배포 플랫폼만 바꿔도 성능이 달라질까

**왜 옮겼나.** 오픈닥터 웹은 AWS Amplify에서 돌고 있었는데, 빌드가 계속 발목을 잡았다. 빌드 시간을 줄이려 캐시 전략을 손봤다가 오히려 2배로 늘어 되돌린 적도 있고, npm registry 빌드 에러 때문에 디자인 시스템을 떼어내야 빌드가 되는 일도 있었다. 웹이 이미 Next.js라 Vercel과의 궁합이 좋을 거란 기대도 있었다.

**그래서 직접 재봤다.** "배포 플랫폼만 바꿔도 Next.js 성능이 달라진다"는 글을 보고, 호기심에 A/B 측정을 했다. **앱 코드는 그대로 두고 호스팅만** Amplify와 Vercel로 나눠, 같은 머신·네트워크에서 약 10분 간격으로 `www.opndoctor.com`을 쟀다. (Lab 1회 · Core Web Vitals는 Chrome DevTools 트레이스, 카테고리는 Lighthouse 모바일.)

| 지표 (Lab) | Amplify | Vercel | 차이 |
| --- | --- | --- | --- |
| **TTFB** | 405 ms | **18 ms** | 🟢 **−387 ms (대폭 개선)** |
| LCP | 914 ms | 957 ms | 🟡 +43 ms (노이즈 범위) |
| CLS (Lab) | 0.06 | **0.00** | 🟢 개선 |
| SEO / 접근성 / BP | 100 / 84 / 69 | 100 / 84 / 69 | = 동일 (앱 코드 같음) |

**가장 확실한 이득은 TTFB — 405ms에서 18ms로.** Vercel 엣지가 서버 첫 응답을 압도적으로 빨리 반환했다. 387ms를 벌었다.

**그런데 LCP는 거의 그대로였다 (914 → 957).** 처음엔 이상했다. 서버가 387ms나 빨라졌는데 화면에 첫 그림이 뜨는 시간은 왜 안 줄지? 파보니 **번 시간을 LCP 이미지 로드에서 다시 까먹고** 있었다. 메인 이미지가 lazy-load·늦은 discovery 상태라, 빨라진 서버 응답을 못 살리는 것이다. → 다음 최적화 1순위가 명확해졌다: 메인 이미지를 HTML 최상단에서 `preload` + `fetchpriority="high"`로 먼저 발견시키기.

**정직하게 짚을 한계.** 각 1회 측정이라 LCP 43ms 차이는 노이즈일 수 있다(신뢰도를 높이려면 3~5회 중앙값). 실사용자(CrUX) 지표는 28일 누적이라 아직 Amplify 시절 값이 섞여 있다 — Vercel의 진짜 성적표는 2~4주 뒤에 나온다. Lighthouse 카테고리가 동일한 것도 정상이다. 호스팅은 속도(TTFB/LCP)만 바꾸고, 접근성·SEO 점수는 앱 코드의 몫이니까.

> 배운 것 — "좋아졌다"를 감으로 말하지 않고 **같은 조건에서 A/B로 재서** 말하니, 무엇이 진짜 이득이고(TTFB) 무엇이 병목으로 남았는지(LCP 이미지)가 또렷해졌다. "왜 Vercel 엣지가 이렇게 빠른가(Edge vs Lambda, v8 isolate·콜드스타트)"는 다음 공부거리로 남겨뒀다.

## 2. 다나와 SEO — png를 html로

**문제.** 의료기기 상세 설명이 **통 이미지(png)** 로 제작·업로드돼 있었다. 보기엔 깔끔하지만 대가가 컸다.

- 크롤러가 이미지 속 텍스트를 **못 읽는다** → 검색 색인에서 통째로 손해
- 스크린리더가 못 읽는다 → **접근성 손해**
- 무거운 이미지 → 로딩·Core Web Vitals 손해
- 문구 한 줄 고치려면 **디자이너가 이미지를 다시** 만들어야 한다

**해결 — 이미지를 구조화된 HTML로.** 의료기기 상세 본문을 **섹션 기반 에디터(body-content)** 로 다시 세웠다. 통이미지 대신 제목·문단·이미지·영상 같은 **섹션들의 조합**으로 상세를 구성하고, 그 구조를 DB의 `spec_content`(jsonb) 컬럼에 저장한다. 운영자는 어드민에서 섹션을 추가하고 순서를 드래그로 바꾸고 유튜브를 임베드하는 것까지 **이미지 없이** 편집한다. 온다·온다 프로 상세부터 실제 HTML로 교체했다.

**하나를 바꿨더니 셋이 좋아졌다.**

- **SEO** — 텍스트가 크롤링·색인 대상이 된다
- **접근성** — 스크린리더가 읽는다
- **운영** — 문구 수정에 디자이너가 필요 없다 (운영자가 바로)

> 배운 것 — "예쁜 이미지 한 장"이 사실은 **검색·접근성·운영의 부채**였다. 5월 미오에서 다국어를 "번역"이 아니라 "구조"로 풀었듯, 이번엔 상세 콘텐츠를 "그림"이 아니라 "데이터"로 풀었다. 보이는 것과 기계가 읽는 것을 분리해서 생각하게 됐다.

## 3. 6월의 문제와 배움

미오 홈페이지에서 **언어(로케일)에 따라 가격이 다르게 보이는 문제**가 터졌다. 다른 자잘한 문제까지 겹쳐 담당자에게 긴급 연락을 받았고, 급하게 달라붙어 수습했다. 정작 오래 남은 건 해결 과정이 아니라 **배움**이었다.

### 화면이 아니라 데이터부터 검증하자

가격이 언어별로 달라 보인 건 결국 데이터 문제였다. 처음엔 화면과 코드를 의심했지만, 답은 **DB에 실제로 뭐가 들어있나**에 있었다. 5월 미오에서 "데이터 설계"로 데었는데, 6월엔 "데이터 검증"으로 다시 돌아온 셈이다.

마침 이 무렵 성욱님(PO)과 **상담 신청 데이터의 정합성**도 주도적으로 파고들었다 — 이름+전화로 중복을 제거하고, 집계의 기준(SSOT)을 잡는 식으로. 숫자가 안 맞을 땐 화면이 아니라 데이터를 봐야 한다는 걸, 한 달에 두 번 배운 셈이다.

### Git에 제대로 데다

6월의 잦은 브랜치·머지 작업 속에서, 그동안 대충 알고 쓰던 Git을 바닥까지 파보게 됐다.

> - **`git pull` = `fetch` + `merge`.** develop에 선 채 `git pull origin main`을 하면, develop tip이 main tip의 조상일 때 충돌·머지커밋 없이 **조용히 fast-forward**된다. 인자 없는 `git pull`은 현재 브랜치의 upstream만 당긴다.
> - **squash merge는 SHA를 새로 쓴다.** 압축 커밋 SHA가 원본과 달라 Git이 머지 여부를 추적 못 해 `not fully merged` 경고가 뜬다 → squash 레포의 브랜치는 항상 `-D`로 삭제.
> - **`git reflog`로 ref 포렌식.** 어떤 명령이 언제 브랜치 ref를 어디로 옮겼는지 사후 추적해 사고 원인을 규명할 수 있다.
> - **머지 전략 혼용의 함정.** main←develop은 머지커밋, develop←feature는 squash로 섞이면 로컬 develop이 main 라인에서 발산한다. `pull.ff-only`·`pull.rebase`가 가드레일이 되지만 한계도 있다.

시켜서가 아니라 **막혀서 배운** 것들이라 오래 남을 것 같다.

### 명확하게 말하는 습관 — 하반기의 진짜 도전

문제를 수습하며 느낀 건, **급할수록 내 말이 흐려진다**는 거였다. 불필요한 수식을 걷어내고 핵심만 명확하게 전하는 것. 사소해 보이지만 이게 하반기 내 진짜 과제다.

마침 좋은 본보기가 가까이 있었다. 팀장님이 메뉴판 정리를 부탁하며 남긴 메시지인데, 예전 같으면 그냥 지나쳤을 문장이 이번엔 다르게 읽혔다.

> 이 스프레드시트가 메뉴판을 정리하는 시트입니다.
>
> - 메뉴가 **변경**되면 표시해 주세요.
> - **삭제**는 행을 지우지 말고, 행을 **빨간 배경**으로 바꿔주세요.
> - **추가**할 행은 추가해 두시면, 확인 후 번역 요청해 홈페이지에 반영하겠습니다.
> - 추후엔 어드민에서 직접 추가·삭제하실 수 있도록 하겠습니다.

무엇을·어떻게·왜, 그리고 앞으로 어떻게 바뀔지까지 한 번에 읽힌다. _"아, 이렇게 말하면 되는구나."_ 명확함은 재능이 아니라 습관이라는 걸, 이 짧은 메시지가 알려줬다.

### 6월 KPT

- **Keep** — 감으로가 아니라 직접 재서(A/B) 말한 것, 인터뷰·데이터를 제품으로 이은 것.
- **Problem** — 급할 때 말이 흐려졌고, 버그를 화면에서 쫓다 데이터 확인이 늦었다.
- **Try** — 말은 불필요한 어구를 걷어내 명확하게, 버그는 DB부터 검증.
