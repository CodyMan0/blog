## 왜 다국어가 제일 까다로웠나

강남의 한 피부과(미오 의원) 홈페이지와 어드민을 혼자 만들게 됐다. 외국인 고객이 중요한 병원이라 **6개 언어**(한국어·영어·일본어·중국어 번체/간체·태국어)가 필요했고, 외주 견적이 값을 제일 크게 매긴 항목도 바로 이 다국어였다.

솔직히 여기서 제일 헤맸다. 다국어를 "어떻게 구현해야 하는지" 자체를 몰랐다.

> ✍️ 채울 것 — 처음에 막막했던 지점 한 장면 (예: 문자열이 코드 여기저기 박혀 있었다 / 번역가에게 뭘 어떻게 넘겨야 할지 몰랐다 / DB 데이터도 번역해야 한다는 걸 뒤늦게 깨달았다).

## 몰라서 쪼갰다 — 정적 vs 동적

아키텍처를 먼저 그린 게 아니다. 제일 먼저 한 건 **문제를 쪼갠 것**이었다. 번역해야 할 문자열을 성격으로 나눠 보니 두 종류였다.

- **정적** — 버튼·라벨·안내 문구처럼 **개발자가 관리**하고 거의 안 바뀌는 UI 문자열
- **동적** — 시술·패키지·카테고리처럼 **운영자가 관리**하고 자주 바뀌는, **DB에 저장되는** 콘텐츠

이 둘은 관리 주체도, 변경 빈도도, 사는 곳(코드 vs DB)도 다르다. 그래서 하나의 방법으로 풀 수 없었다. **정적은 정적대로, 동적은 동적대로** 다른 시스템을 만들기로 했다. 돌아보면 이 분해가 사실상 첫 번째 설계 결정이었다.

## Layer A · 정적 UI — 번역가는 git을 못 쓴다

정적 문자열의 핵심 제약은 기술이 아니라 **사람**이었다. 번역은 내가 만들 수 없고, 번역가는 git·PR·JSON을 다루지 않는다. 찾아보니 이런 경우 **스프레드시트 기반 워크플로우**가 흔한 방식이었다.

그래서 `next-intl` + 언어별 `messages/{locale}.json`을 두고, 코드와 구글 시트를 잇는 **동기화 스크립트 두 개**를 만들었다.

```
ko.json에 새 키 추가  →  pnpm i18n:export  →  [ 구글 시트 ]  ← 번역가가 6개 언어 채움
                                                    ↓
                        로컬 {locale}.json  ←  pnpm i18n:pull
```

- `i18n:export` — 로컬 JSON을 평탄화해 **시트를 통째로 다시 쓴다.** 즉 *키 구조의 원천은 코드*다.
- `i18n:pull` — 시트를 읽어 **로컬 JSON을 통째로 덮어쓴다.** 즉 *번역 값의 원천은 시트*다.

머지나 충돌 해결 로직은 **일부러 만들지 않았다.** 대신 규율로 풀었다 — **"키는 코드에서만 추가하고, 값은 시트에서만 채운다."** 단순함을 택한 대가로 규율이 필요한 트레이드오프다.

디테일 둘. 중첩 JSON을 시트의 2차원 표에 맞추려고 **flatten ↔ unflatten**(점 표기 키)을 거쳤고, 시트의 행 순서는 손으로 의미별로 묶어 둔 **`ko.json`의 순서를 기준(canonical)**으로 삼았다.

> ✍️ 채울 것 — 이 파이프라인을 만들며 실제로 겪은 일 하나. (예: 번역가가 시트를 어떻게 받아들였나 / export·pull 규율을 어기고 시트에서 키를 바꿨다가 깨진 사건 / 처음엔 수동으로 하다가 스크립트로 바꾼 계기)

## Layer B · 동적 DB — 번역 테이블 대신 JSON 컬럼

DB에 저장되는 콘텐츠는 시트로 풀 수 없다. 운영자가 어드민에서 **실시간으로 편집**하니까. 그래서 DB에 직접 넣되, 로케일마다 행을 만드는 **번역 테이블 대신** 각 필드를 **JSON 컬럼** 하나로 뒀다.

```prisma
model Treatment {
  name             Json // i18n
  shortDescription Json @map("short_description") // i18n
  description      Json // i18n
  tags             Json // i18n (locale -> comma-separated tags)
  // ...
}
```

이유는 세 가지였다. **(1)** 조인을 피하고 읽기를 단순하게 — 한 행을 읽으면 모든 언어가 딸려온다. **(2)** 한 모델에 번역할 필드가 여러 개(`name`·`description`·`tags`…)라, 필드마다 번역 테이블을 만들면 폭발한다. **(3)** 일단 빠르게 가려는 단순 설계.

읽을 때는 작은 헬퍼 하나로 로케일을 골라낸다. 번역이 비어 있어도 화면이 깨지지 않도록 **폴백 체인**을 뒀다.

```ts
export function pickI18n(field: I18nField | string | null | undefined, locale: Locale): string {
  if (typeof field === 'string') return field
  if (!field) return ''
  const key = toApiLocale(locale)
  return field[key] || field.en || field.ko || ''   // locale → en → ko → ''
}
```

> ✍️ 채울 것 — JSON 컬럼의 대가. (예: 특정 로케일만 조건으로 거는 쿼리·인덱싱이 어렵다 / 나중에 실제로 이 한계에 부딪힌 적이 있나?)

## AI 초벌 + 사람 검수 — 번역 상태를 추적하다

동적 콘텐츠는 양이 많아서 사람이 6개 언어를 다 채울 수 없었다. 그래서 **AI로 초벌 번역**을 만들고 사람이 검수해 확정하는 흐름으로 갔다. 문제는 "어떤 필드가 아직 AI 초벌이고, 어떤 게 사람 검수를 거쳤나"를 알 수 없다는 것. 그래서 번역 메타데이터를 별도 테이블로 추적했다.

```prisma
model TranslationMeta {
  field   String
  locale  String
  source  String @default("ai") // ai, ai_reviewed
  aiValue String @default("") @map("ai_value")
  // (contentType, objectId) 로 어떤 레코드의 어떤 필드인지 가리킨다
}
```

`source`가 `ai`면 아직 미검수, `ai_reviewed`면 사람 손을 탄 것. 덕분에 **미검수 필드만 골라내** 검수 대상을 관리할 수 있었다.

> ✍️ 채울 것 — AI 번역을 실제로 어떻게 돌렸나(모델·프롬프트·배치?), 그리고 이 추적이 운영에서 얼마나 쓰였나(솔직하게 — 잘 안 썼으면 그것도 기록).

## 물려받은 스키마 — Django에서 Node로

흥미로운 지점. 이 동적 다국어(JSON 컬럼) 방식은 사실 **내가 처음 만든 게 아니라 이어받은 것**에 가깝다. 스키마 곳곳에 이전 백엔드의 흔적이 남아 있다 — `DjangoContentType` 모델, Django식 제약명, 그리고 `rename_django_tables` 마이그레이션.

> ✍️ 확인해서 채울 것 — 이 히스토리의 진짜 순서. 초기 미오 백엔드가 **Django였다가 Node/Prisma로 다시 세운 것**이 맞나? 그렇다면 "남의(이전) 스키마를 이어받아 다시 세우기"는 그 자체로 이 글의 한 축이 된다. (마이그레이션 기록상 6월에 Django 테이블을 넘겨받아 정리한 흔적이 있음.)

## 배운 것 / 지금이라면 다르게

- 다국어의 본질은 "번역"이 아니라 **"번역이 계속 굴러가게 만드는 구조"**였다. 만드는 시간보다 *굴러가게 유지하는 구조*를 짜는 게 핵심이었다.
- 몰랐기 때문에 **문제를 쪼갠 것**이 오히려 제일 좋은 결정이었다.

> ✍️ 채울 것 — 지금이라면 다르게 할 것 한두 가지. (예: JSON 컬럼의 쿼리 한계를 알았으니 일부는 정규화했을 것 / export·pull에 검증·CI를 붙였을 것 / 검수 워크플로우를 어드민에 통합했을 것)
