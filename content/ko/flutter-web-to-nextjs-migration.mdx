## 문제: SEO가 불가능한 Flutter-web

오픈닥터는 의사·의료인이 개원 입지를 분석하고 의원 매물을 검색하는 메디컬 부동산 플랫폼이다. 서비스 전체가 Flutter-web으로 구축돼 있었다.

Flutter-web은 캔버스 기반으로 렌더링되기 때문에 검색 엔진이 콘텐츠를 크롤링할 수 없다. 결과는 명확했다.

- **월 노출 9,390회에 정체** — 하루 노출 313회, 실제 클릭(유입) 하루 10명 남짓
- _"강남 피부과 개원 분석"_ 같은 자연 검색으로 유입되는 경로가 **사실상 없었다**
- FCP **15.9초**, LCP **18초** — 첫 화면이 뜨는 데만 15초 이상 걸렸다

유지보수 문제도 심각했다. 지도 영역 하나를 수정하려면 3개 프로젝트를 동시에 실행해야 했고, 개발 서버에서 UI 변경 결과를 확인하는 데 **15~30초씩** 기다려야 했다.

## 제약: 한 번에 갈아엎을 수 없다

그렇다고 Flutter-web을 한꺼번에 걷어낼 수는 없었다. 이유는 두 가지였다.

1. **운영 중인 서비스** — 의사 고객이 실시간으로 사용하고 있다
2. **프로젝트 규모** — 입지 분석·매물·의원·리포트 등 여러 도메인이 존재한다

"서비스 중단 없이, 조금씩" — 이 제약이 설계 방향을 결정했다.

## 해결 설계: 이중 iframe 아키텍처

### 1단계 [2025년 7월] — Flutter 안에 React 넣기

먼저 Flutter-web 안에 React로 개발할 수 있는 환경을 구축했다. 작은 기능(상담 신청 등)부터 React로 교체하며 점진 전환의 발판을 마련했다.

### 2단계 [2025년 11월] — Next.js를 최상위로

SEO 작업이 시급해지면서 팀 논의 끝에 아키텍처를 근본적으로 바꾸기로 했다.

![img alt="asis-tobe"](/img/study/asis-tobe.png)

**핵심 아이디어**: Next.js를 최상위(부모)에 두어 SEO를 챙기고, 기존 Flutter-web은 그 안에 iframe으로 삽입한다. 사용자에게는 변화가 없고, 검색 엔진에는 Next.js의 SSR HTML이 노출된다.

```
Next.js (부모, SEO 담당)
  └─ iframe: Flutter-web (기존 서비스 유지)
       └─ iframe: React (점진 전환 영역)
```

부모-자식 간 통신은 **PostMessage**로 처리했다. 도메인·쿠키 인증 동기화, URL 동기화, 새로고침 시 통신 끊김 문제 등을 단계적으로 해결했다.

### 3단계 [2026년 2월] — AI-friendly 업무 쪼개기

마이그레이션 범위의 50%를 완료한 시점에서 속도를 높이기 위해 업무 방식을 바꿨다. 프로젝트에는 AI가 모르는 맥락이 많았다 — "이 부분은 iframe이고, 상태는 이렇게 관리한다" 같은 내용들.

**해결책**: 작업을 잘게 쪼개고, 쪼개진 작업에 해당하는 맥락만 주입했다.

![img alt="work-list"](/img/study/work-list.png)

이 과정에서 중요한 것을 깨달았다. **AI에게 문제를 명확하게 나누어 요청하는 것이 핵심이다. 기획은 사람이 해야 한다.**

### 4단계 [2026년 3월] — 피처플래그로 안전망 확보

마무리 단계에서 팀원의 제안으로 **피처플래그**를 도입했다.

![img alt="feature-flag"](/img/study/feature-flag.png)

- **배포 환경**: 환경 변수로 Next.js 화면을 보일지 Flutter 화면을 보일지 결정 → 문제 발생 시 즉시 롤백 가능
- **개발 환경**: UI 토글로 Next.js ↔ Flutter 화면을 나란히 비교하며 누락 기능·버그를 빠르게 검증

이 덕분에 마이그레이션 완료 도메인에 대해 기능 검증과 롤백 모두 안전하게 진행할 수 있었다.

## AI 활용 방식

마이그레이션 초반에는 백엔드 API의 DTO·Entity를 직접 분석하고, 화면 변화를 일일이 추적하며 Next.js로 구현했다.

중반부터는 방식을 바꿨다:

1. AI에게 DTO·Entity와 화면 설계를 분석시킨다
2. AI가 이해한 내용을 확인하고, Next.js 구현 방향을 AI와 논의한다
3. 구현을 AI에게 맡긴다

**"기획은 사람이, 구현은 AI와"** — 이 프로세스가 마이그레이션 후반부 속도를 결정했다. 작업을 잘게 쪼개는 것, 즉 맥락을 좁혀서 AI에게 전달하는 것이 AI 활용의 핵심이었다.

## 배운 것

**기술적으로**: iframe 중첩 아키텍처는 Safari ITP(Intelligent Tracking Prevention)와 충돌한다. Flutter-web이 사용하는 `FlutterSecureStorage`(WebCrypto + IndexedDB 기반)가 Safari의 third-party 스토리지 파티셔닝에서 hang 상태에 빠지는 문제를 실제로 겪었다. 해결 방법은 직접 읽기 제거 → 인메모리 토큰으로 전환이었다.

**프로세스적으로**: 점진 마이그레이션의 핵심은 "언제든 되돌릴 수 있는 구조"다. 피처플래그가 없었다면 배포할 때마다 긴장해야 했을 것이다.

**AI 협업에 대해**: AI는 구현을 잘하지만, 프로젝트 고유의 맥락을 모른다. 맥락을 좁혀서 주는 것 — 즉 작업을 쪼개는 것 — 이 결국 사람의 역할이자 AI를 잘 쓰는 방법이다.

> 운영 중인 서비스를 멈추지 않고 기술 스택을 바꾸는 것은 달리는 기차의 바퀴를 교체하는 일이다. 설계가 전부다.
