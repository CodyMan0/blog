> 초안. 데스크탑에서 대화하며 채운다.

## 요구 사항 — 팝업이 생각보다 까다로웠다

웹에 이벤트 팝업을 넣는 일을 맡았다. 겉보기엔 간단한 기능이지만 요구 사항을 정리하고 나니 결정할 게 여러 개였다.

- 특정 기간에만 팝업을 등장시킨다.
- 팝업의 추가·삭제를 클라이언트 코드 수정 없이 할 수 있어야 한다.
- 팝업이 여러 개일 수 있다.

"어떻게 구현하는 게 정답에 가까울까"를 계속 물으면서, 저장 위치를 두 층으로 나눠 생각하게 됐다. 하나는 팝업을 켜고 끄는 주도권을 어디에 둘 것인가, 다른 하나는 "이 사용자가 팝업을 닫았다"는 사실을 어디에 남길 것인가였다.

## 팝업의 주도권 — 서버 API로 둔다

먼저 팝업 자체를 켜고 끄는 권한이었다. 클라이언트 코드를 고치지 않고 팝업을 추가·삭제하려면, 팝업의 존재 여부가 배포된 코드가 아니라 서버 데이터에 있어야 했다. 그래서 settings 성격의 테이블에 key, value 형태로 저장하는 방식을 택했다.

```
pop_up#a3f8d2
pop_up#9b4e21
```

value에는 팝업 하나를 그리는 데 필요한 정보를 담는다.

```ts
type Popup = {
  id: string;          // 예: "a3f8d2"
  name: string;        // 팝업 이름
  description: string; // 팝업 설명
  imageUrl: string;    // 팝업 이미지 주소
  linkUrl: string;     // 클릭 시 이동
  isActive: boolean;   // 이 팝업을 지금 보여줄지 말지 — 가장 중요한 스위치
};
```

여기서 핵심은 `isActive`였다. 이 값 하나로 팝업을 켜고 끌 수 있으면, 팝업을 내리거나 새로 올리는 일이 클라이언트 배포와 무관해진다. 솔루션 웹 쪽에 이 스위치를 켜고 끄는 화면을 붙이는 것까지 가면, 개발자가 아닌 사람도 팝업을 관리할 수 있게 된다.

## 닫힘 상태 — 로컬스토리지냐 쿠키냐

두 번째 층은 "사용자가 이 팝업을 닫았다" 혹은 "오늘 그만 보기를 눌렀다"는 사실을 어디에 남길 것인가였다. 이건 서버가 굳이 알 필요가 없는, 브라우저 하나에만 국한된 정보였다. 후보는 로컬스토리지와 쿠키 두 가지였다.

로컬스토리지는 데이터가 사용자의 브라우저에만 저장된다. 서버로 API를 요청하거나 페이지를 이동할 때 함께 전송되지 않는다.

- 장점: "팝업을 숨겼다"는 정보는 오직 브라우저만 알면 된다. 서버로 불필요한 데이터를 보내지 않으니 네트워크 낭비가 없다.
- 단점: 쿠키처럼 만료 옵션이 없다. 그래서 "언제까지 숨김"이라는 만료 타임스탬프를 코드에서 직접 계산하고 비교해야 한다.

쿠키는 브라우저에 저장되지만, 서버로 요청을 보낼 때마다 HTTP 헤더에 자동으로 포함되어 전송된다.

- 장점: `expires`나 `max-age` 옵션이 내장되어 있어 "내일 0시까지 유효" 같은 만료 로직을 브라우저에 맡길 수 있다. 코드가 조금 더 간단해진다.
- 단점: 서버는 팝업 표시 여부에 전혀 관심이 없는데도, 모든 요청에 불필요한 팝업 쿠키 데이터가 실려 나간다. 리소스 낭비다.

```
팝업 닫힘 상태를 어디에 남기나?

localStorage ── 서버로 안 감 ── 만료는 내가 타임스탬프로 계산
cookie ─────── 매 요청에 실림 ── 만료는 브라우저가 알아서
```

## 결정 — 켜고 끄기는 서버, 닫힘은 로컬스토리지

정리하면 이렇게 나눴다. 팝업을 추가하고 삭제하는 주도권은 서버가 갖도록 테이블 하나와 API 하나를 두고, "이 사용자가 팝업을 닫았다"는 정보는 로컬스토리지에 남기기로 했다.

로컬스토리지를 고른 이유는 명확했다. 팝업 닫힘 여부는 서버가 알 필요가 없는 정보인데, 쿠키를 쓰면 그 정보가 관계없는 모든 요청에 계속 실려 나간다. 만료를 직접 계산해야 하는 수고는 있지만, 그 대가로 불필요한 네트워크 비용을 없애는 편이 맞다고 봤다.

## 마무리 — 저장 위치는 "누가 알아야 하는가"로 갈렸다

이 작업에서 배운 건, 저장 위치를 고를 때 "이 정보를 누가 알아야 하는가"를 먼저 물으면 답이 쉽게 갈린다는 점이었다. 팝업의 존재와 활성 여부는 여러 사용자와 관리자가 공유해야 하니 서버가 가진다. 팝업을 닫았다는 건 그 브라우저 하나만 알면 되니 로컬에 남긴다. 같은 "저장"이라도 정보의 소유자가 다르면 위치가 달라진다는 걸 팝업 하나로 다시 확인했다.
