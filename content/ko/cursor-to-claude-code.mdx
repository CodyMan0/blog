## 왜 갈아탔나

솔직히 말하면 내가 먼저 갈아타겠다고 결정한 게 아니었다.

2025년까지 Cursor를 3개월 넘게 써왔다. MCP도 제대로 쓰지 않았고, 피그마 스크린샷을 던져주며 "이대로 구현해줘"라고 하는 수준이었다. 결과가 좋을 리 없었지만, 당시엔 그게 이상한 것도 아니었다.

전환의 계기는 사내 AI 스터디였다. 회사에서 전사 AI 스터디가 생겼고, 동료 개발자 규석님의 건의로 개발팀 전체 Max 플랜이 승인됐다. 그 기회에 Claude Code로 넘어갔다. ShoutOut to 규석님.

"AI로 생산성 극대화했다"는 이야기는 반신반의했다. 직접 써보기 전까지는.

## 실제로 뭐가 달라졌나

### 수치로 먼저 말하면

오픈닥터에서 회원가입 + 의료인 면허 인증 기능을 구현하는 작업이 있었다. 기능 목록을 나열하면 이렇다.

**회원가입**
- 화면 컴포넌트(퍼블리싱)
- UI 유효성 검사
- 서버 통신
- 백엔드 API 수정
- Flutter-web ↔ iframe 기반 인증 통신

**의료인 면허 인증**
- 화면 컴포넌트(퍼블리싱)
- UI 기능(실패 횟수 초과 시 안내 문구 등)
- 서버 통신

Cursor를 쓰던 감으로 잡은 예상 일정은 **1스프린트(10 working days)**였다. 입사 후 6개월 경험을 바탕으로, 기능을 다 더하면 2주는 걸린다고 판단했다.

Claude Code로 전환하고 작업해보니 **구현 2일 + 테스트 3일 = 총 5일**이었다. 예상의 딱 절반.

### 왜 빨라졌나

이 결과가 나온 데는 몇 가지 이유가 있다.

**1. 피그마 MCP**

Cursor를 쓸 때는 피그마 스크린샷을 캡처해 붙여넣었다. Claude Code에서 피그마 MCP를 연결하니 AI가 피그마를 직접 읽는다. 디자인 시스템이 피그마에 있으니 퍼블리싱 관련 커스텀 스킬을 만들어주었더니 결과물이 확연히 달라졌다. "이 화면 구현해줘"에서 "피그마 파일의 이 프레임을 구현해줘"로 바뀌면서 대화 품질이 달라졌다.

**2. `/add-dir`로 여러 프로젝트 맥락 동시 접근**

우리 서비스는 마이그레이션 중이라 iframe 통신이 많다. Next.js(부모) → Flutter-web → React 구조로, 인증 하나를 건드리려면 3개 프로젝트를 동시에 이해해야 한다.

Cursor에서는 프로젝트 하나씩밖에 못 열었다. Claude Code의 `/add-dir` 명령어로 iframe 통신하는 3개 프론트엔드 프로젝트의 코드베이스를 하나의 세션에 올렸다. 체감 작업 능률 300% 증가라고 표현했는데, 그게 과장이 아니었다. 불필요한 컨텍스트 스위칭이 사라지고, AI가 프로젝트 간 연결 고리를 이해한 상태로 코드를 짜주니 엉뚱한 오류가 훨씬 줄었다.

**3. PO의 PRD**

이건 도구의 문제가 아니라 협업의 문제인데, PO 성욱님이 PRD를 잘 써주셨다는 게 결정적이었다. AI가 PRD를 읽고 작업하니 의도 맥락이 끊기지 않았다.

**4. 도구 전환에 대한 거부감을 버린 것**

익숙함 때문에 Cursor를 3개월 고집했다. Claude Code가 낯설어도 빠르게 전환한 것 자체가 생산성에 기여했다.

## 아쉬운 점

**터미널 기반 진입 장벽**

Cursor는 VSCode 위에 AI를 얹은 형태라 적응이 빠르다. Claude Code는 CLI 툴이다. 터미널을 편하게 쓰는 개발자라면 문제없지만, 처음에 "뭘 어떻게 쓰는 거지?" 하는 온보딩 마찰이 있다. 공식 문서를 한 번 읽고 시작하는 걸 권장한다.

나는 회사에서 Max 플랜을 지원받아 전환했기 때문에 개인 비용 부담이 없었다. 개인 비용으로 쓴다면 플랜 선택과 사용량을 직접 비교해봐야 한다. Cursor Pro 대비 Claude Code의 가격 구조가 다르므로, 하루 사용량을 먼저 가늠해보는 걸 권장한다.

**컨텍스트 관리**

세션이 길어지면 컨텍스트 창이 차오르는 게 보인다. 작업을 적절히 분리하고 새 세션을 여는 습관이 필요하다. 이 부분은 Cursor도 크게 다르지 않지만, Claude Code에서 더 명시적으로 신경 써야 한다는 느낌이다.

## 결론 — 갈아탈 가치 있나?

**있다.** 단, 조건이 있다.

다음 상황이라면 전환을 강하게 권장한다.

- 동시에 여러 프로젝트(monorepo, iframe 통신, 마이크로프론트엔드 등)를 넘나드는 작업을 한다
- 피그마를 자주 보면서 구현하는 퍼블리싱 작업 비중이 높다
- PRD나 스펙 문서가 잘 정리돼 있는 팀에 있다
- 터미널 환경에 거부감이 없다

반면 다음 경우라면 Cursor에서 시작해도 충분하다.

- IDE 인라인 자동완성 위주의 작업이 많다
- 단일 프로젝트 코드베이스에서 작업한다
- 온보딩 마찰 없이 바로 쓰고 싶다

나에게 결정적이었던 건 `/add-dir`로 여러 프로젝트를 하나의 세션에서 다룰 수 있다는 점이었다. iframe 통신이 얽힌 멀티 프로젝트 환경에서 이 기능 하나가 체감 생산성을 완전히 바꿨다. 예상 10일 작업이 5일로 줄었다는 숫자는 운이 아니었다.

도구보다 중요한 건 어떻게 쓰느냐다. 피그마 MCP 연결, 여러 프로젝트 맥락 주입, 좋은 PRD — 이 세 가지가 맞물렸을 때 Claude Code는 확실히 달랐다.
