- 인증·세션 관련 PR **106건** — 토큰 브리지, 회원가입/로그아웃 상태 전파, Safari 스토리지 이슈, 서버 영속화

## 실제로 한 일

Flutter-web(구)과 Next.js(신)가 한 도메인에서 같이 돌아가는 동안, 어느 쪽에서 로그인해도 반대편이 즉시 같은 상태여야 했다. 새로고침·로그아웃·회원가입 각각에서 전파 경로가 달랐고, Safari에서는 스토리지 파티셔닝 때문에 아예 다른 해법이 필요했다.

관련 글: Safari ITP와 iframe 스토리지 파티셔닝 (기존 초안 있음)

## 예상 꼬리 질문

1. 토큰을 **어디에 뒀나.** localStorage / 쿠키 / 메모리 중 무엇이고 왜인가. XSS·CSRF 각각에 대해 뭘 감수했나.
2. 두 앱 사이 전달은 **postMessage인가.** origin 검증은? 누가 보내고 누가 신뢰하나.
3. **무한 렌더링**(web#188)은 왜 났나. 상태 갱신 루프의 구조를 설명할 수 있나.
4. 로그아웃이 **한쪽에만 반영되는** 경우는 없었나. 원자성은 어떻게 보장했나.
5. Safari ITP에서 iframe 안 스토리지가 막히는 **정확한 이유**는? Storage Access API로 왜 안 풀리나.
6. 리프레시 토큰 회전은? 동시에 여러 탭에서 만료되면?
7. 진료과 필터를 **서버에 영속화**한 건 인증 문제인가 UX 문제인가. 비로그인 사용자는?

## 확인 필요

- 실제 토큰 저장 위치와 만료 정책
- postMessage origin 검증 코드가 지금도 남아 있는지

## 파볼 층

- 1층: 상태를 어떻게 전달했나 (postMessage / 스토리지 / 서버)
- 2층: **브라우저 오리진** — 왜 origin이 신뢰의 단위인가. 쿠키·스토리지 파티셔닝
